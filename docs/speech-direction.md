# 配音设定、发音词表与生成记录

工作台按项目保存共同背景与表演基调，逐句生成时结合当前场景和相邻对白，再按照实际音色所属模型的能力构造请求。新台本在原有 LLM 生成步骤中同时产出整场表演设计；配音时使用规则和已确认设计，不增加逐句 LLM 调用。

## 使用入口

1. 打开项目工作台，点击顶部 **配音设定**。
2. 填写 **作品背景摘要**：时代、人物关系、长期动机、整体氛围。不要直接粘贴整本小说。留空时依次采用本章已提交改编的解析梗概、项目简介；没有这些信息时提示补充，不自动编造。
3. 填写 **共同表演基调**，例如“生活化接话，人物声线稳定；悬疑感主要由停顿呈现，普通问答保持平稳”。不同小说可保存不同基调，同一本混合题材小说仍按当前场景理解。
4. 添加人名、地名、多音字或缩写的 **发音词表**。每条至少填写拼音或替代读法。
5. 保存后，在对应台词点击 **生成输入与记录**，核对当前输入预览。预览只读已保存台词；未保存的编辑不在预览中。
6. 之后按原有方式生成、试听和选择版本。设定改变不会自动重生成已有音频，也不会使原有版本消失。

静态演示不提供这些后端入口。修改代码后需重启本地后端并刷新前端，数据库表在启动时建立。

## 旁白怎样处理

不设统一旁白比例、固定单句字数或连续旁白禁令。当前生成、独立审核、返修和旧拆分入口共享这一原则；旧数据库模板中的默认数值限制由共享规则覆盖，用户明确指定的叙述风格仍有效。

判断依据是叙事功能：旁白可以交代时间地点转换、压缩经过、表达不能自然外化的心理活动、建立叙述者视角或保留有听觉价值的文学语言。对白或声音已经表达清楚的信息应避免无意义重复。不要为了减少旁白而让角色生硬地解释双方都知道的事，也不强迫每场插入音效。

例如，“三年后，他回到那座已经停用的车站”未必能靠火车声表达准确；必要旁白可以保留。“门关上了”若只是重复清晰的关门声，则可以删除，除非叙述视角另有作用。

旁白占比、长句数和连续条数仅作描述性观察，不自动判为错误或扣分。BBC 的广播剧格式允许叙述声与对白、音效、音乐组合；本项目的功能判断是基于制作需要的设计选择，不把比例宣称为行业标准。[BBC 广播剧格式](https://downloads.bbc.co.uk/writersroom/scripts/radious.pdf)

## 整场表演设计

新生成及返修台本的每个场景包含共同表演基调、接话节奏、人物在当下的目标与关系，以及按顺序推进的表演阶段。每句人物声与旁白绑定当前阶段，说明本句意图、局部表达和正在回应的前文。默认不标记情绪突变；必要转折须附原文或用户要求中的直接引用。

台本确认卡中可展开 **整场表演设计**，结合各句意图审阅；需要调整时，通过制作助手反馈修改，再选用对应台本版本。设计与台本一起确认、提交和保留版本。制作阶段在每句 **生成输入与记录** 中查看实际采用的设计及当前阶段。

结构校验拒绝不存在的阶段、逆序阶段、缺失的人物目标，以及指向未来台词或音效的接话引用。独立审查检查表演要求和剧情的语义一致性；程序另外核对转折引用是否确实出现在原文或用户要求中。引用存在不等于语义正确，仍需结合原文审阅。

提交时设计绑定真实台词 ID，不依赖可能重复的场景标题。改动正文、角色、顺序、情绪标签或声音指导后，该场旧设计会在配音时标记过期并停用，回到当前项目基调和相邻台词；可通过台本返修重新生成并审阅。音频生成状态或音频版本变化不会使设计过期。

原生 TTS 收到当前人物和当前阶段的指导，不附整场后续高潮的表演指令。短指令模型仅使用能容纳的局部指导；完整设计仍保留在记录中供检查。旧台本没有设计时继续兼容，不自动调用模型补造设计，也不改动旧音频。

## 上下文与连续性

当前生成记录保存作品背景、章节与场景、说话人、声线说明、本句指导、同一连续场景的前两句和后一句对白，以及同人物最近一次发言。相邻台词与背景不会拼到待朗读正文；原生指令明确要求只读本句，后文只用于接话，不提前表演人物尚未知晓的信息。

默认根据台本顺序限制同人物无依据的强度突增：从日常交谈基线开始，每次发言最多上升一档；有效的整场设计按已核对引用的转折标记放行；没有设计或设计过期时，沿用本句明确的转折指导。不借用其他人物的强度，跨场景重新开始。向下变化不提高原本选定的弱情绪，避免连续性处理反而加重表演。原标签不改写，记录同时显示原档位与本次实际采用的档位。

剧情确实需要骤变时，在本句声音指导中明确写“情绪转折”及具体表达，例如“情绪转折，认出对方后喊出名字，随后停住”。识别是保守规则，不能理解所有自然语言；也可在项目配音设定关闭强度控制。

这些措施提供的是文字上下文和强度约束。当前没有把上一句音频作为声学上下文送入模型，没有自动判断两段录音的音色、气口和情绪是否连续，也不保证实际读音或听感。最终仍需连播试听。

## 按模型处理

| 实际模型或音色能力 | 指导与上下文 | 词表 |
| --- | --- | --- |
| Qwen-Audio 3.0 Plus / Flash | 使用 `input.instruction`，包含克制表演指导与有长度限制的背景、接话信息 | 内置 HTTP 请求使用 `input.hot_fix.pronunciation`；拼音优先于替代读法 |
| Qwen3 TTS Instruct | 使用 `input.instructions`；默认关闭 `optimize_instructions`，避免额外优化改变指导意图 | 当前未接入原生拼音字段，可用替代读法 |
| CosyVoice 原生指令音色 | 按官方 100 加权字符限制保留完整分句（汉字计 2）；基础表演约束后放本句指导，缺省时放共同基调，不能容纳完整小说上下文 | 当前可用替代读法 |
| CosyVoice 固定情绪 / 参数映射音色 | 仅发送支持的固定情绪或韵律参数；完整背景留在记录中供排查 | 当前可用替代读法 |
| Edge / 不支持原生指令的模型 | Edge 使用语速、音高和音量；不把完整背景伪装成已执行的指令 | 当前可用替代读法 |
| 自定义 HTTP 模板 / 旧情绪向量接口 | 自定义模板必须配置指导占位符或支持的字段；旧接口沿用情绪向量。以最终请求为准 | 自定义模板不自动注入厂商拼音字段，可用替代读法 |

长上下文会按字段缩短用于模型的版本，完整的本次上下文快照仍可检查。CosyVoice 的短预算可能使后面的具体指导未进入请求，请以 **最终请求预览** 中的字段为准。其他原生模型增加保守的本地长度预算：不足时按优先级舍弃完整上下文字段，预览明确列出未发送内容；不会把后续阶段塞入剩余空间。本句指导本身过长时，在发送请求前报错。该预算按加权字符计数，并非厂商的精确 tokenizer，服务端限制仍适用。

例如，词条 `重庆` 的拼音可填 `chong2 qing4`。不支持拼音控制的模型若只有拼音、没有替代读法，预览会明确提示“未应用”。替代读法只修改本次 TTS 正文，不改原台词与字幕；多个词同时命中时先匹配较长词，替换结果不会继续触发其他词条。英文正文保留词间空格。

Qwen 的 `extra_payload.input` 现在合并补充字段，不再整体抹掉正文、音色或词表。若使用完整 `payload` / `body` 模板，仍以模板序列化结果为准。

官方协议：[Qwen-Audio / CosyVoice HTTP](https://help.aliyun.com/zh/model-studio/cosyvoice-tts-http-api)、[Qwen TTS](https://help.aliyun.com/zh/model-studio/qwen-tts-api)、[CosyVoice 非流式调用](https://help.aliyun.com/zh/model-studio/non-realtime-tts-user-guide)。能力取决于模型版本和实际音色，不只看项目默认提供商。

## 生成记录保存什么

复用本地 SQLite 的 `project_speech_profiles` 与 `tts_generations` 表。迁移版本 8 为章节增加可空的 `performance_plan` 字段，保存已确认设计、台词绑定和源内容指纹；旧章节正文与录音不重写，无需另行部署数据库。

每次工作队列实际开始生成时创建独立记录，保存：

- 原台词、处理后正文、声音指导、上下文快照、设定版本、实际模型与音色、原始和采用的情绪强度、词表处理与提示。
- 发出前的最终 HTTP 请求体或 SDK 调用参数。认证请求头不落库；配置的 API Key、常见凭证字段和 URL 签名查询参数脱敏。
- 收到的 HTTP 状态、可用的 JSON 返回或 SDK 请求 ID、用量/文本/时间戳等元数据（以接口实际提供为准）。音频本体不重复存入日志；只存大小和摘要。
- 成功/失败状态、错误信息、起止时间、任务 ID 和关联的生成音频版本。

准备阶段就失败时，保留排队台词和错误，实际请求为空；网络失败或 SDK 未返回可记录结果时，返回栏为空。进程异常退出或超时后，可能保留“未完成”或失败记录；历史记录不自动重试模型请求。旧音频不会补造历史请求。删除台词后该项目仍保留其记录，可用项目级 API 查询；删除整个项目会一并清理记录。

接口支持按项目/台词查询与分页：

- `GET /projects/{project_id}/speech-settings`
- `PUT /projects/{project_id}/speech-settings`
- `GET /projects/{project_id}/lines/{line_id}/speech-preview`
- `GET /projects/{project_id}/tts-generations?line_id=...&limit=10&before=...`

TTS 的文字返回通常是接口数据，并非“为什么这样表演”的解释；返回原文也不能证明实际读音正确。排查应先对比台词、模型实际收到的指导与邻句，再连播试听。判断漏读/错读需要后续人工或 ASR 校验，当前不自动执行。

## 是否需要额外模型或 Agent

现阶段先使用可检查、可复现的上下文组装，避免每句额外调用一个模型又引入风格漂移。现有章节解析已提供可复用的梗概，缺少全书背景时由项目设定补充。

当前已把场景级表演设计加入原有台本生成和返修调用，沿用项目的 LLM 配置与现有重试机制。没有新建逐句提示词模型，也没有自动试听、评判和重生成的 Agent。下一步是否增加声学检查，应由真实试听问题和对照测试决定。

只有需要模型自主选择工具、比较试听结果、定位问题并决定局部重生成时，Agent 才提供额外价值。增加 Agent 本身不会消除错误台词或情绪跳变；OpenAI 的编排文档也建议先建立明确的单一职责，再按实际需要拆分。[Agent 编排](https://developers.openai.com/api/docs/guides/agents/orchestration)
